Validation against the Budget Lab at Yale's tax-simulator-gpu
=============================================================

This folder compares Tax-Calculator's **federal** income and payroll
tax results with those of the Budget Lab at Yale's
[tax-simulator-gpu](https://github.com/Budget-Lab-Yale/tax-simulator-gpu)
(TS), a Python (JAX) microsimulation model that replaces the Budget
Lab's R [Tax-Simulator](https://github.com/Budget-Lab-Yale/Tax-Simulator),
for random samples of filing units in each year 2023 through 2025.
Only income and payroll taxes and their components are compared:
tax-simulator-gpu's estate and wealth taxes are ignored.  Each
validation sample is identified by an assumption-set letter `L` (`a`,
`b`, or `c`) and a two-digit year `YY`.  The comparison involves five
steps:

1. [`../common/generate_sample.py`](../common/generate_sample.py),
   which is shared with other validation workflows, writes a
   TAXSIM-formatted sample `samples/LYY.in.csv.gz`
   (always `state=0`, `idtl=2`) containing joint (40%), head of
   household (30%), single (15%), and married filing separately (15%)
   filing units.  With `--workflow tbly_ts`, the samples have at most
   three dependents, because tax-simulator-gpu records only three
   dependent ages, and its `--all` option writes all nine samples.
2. `run_ts.py` runs the pinned tax-simulator-gpu income and payroll tax
   calculator on the sample (through `ts_batch.py`, which runs in the
   tax-simulator-gpu environment) and writes
   `ts_output/LYY.out-ts.csv.gz` plus a version stamp
   `ts_output/LYY.out-ts.stamp.json`.
3. [`../common/taxsim_to_tc.py`](../common/taxsim_to_tc.py)
   translates the sample into a Tax-Calculator input file.
4. [`../common/run_tc.py`](../common/run_tc.py) runs the
   Tax-Calculator CLI with the `ts_emulation.json` reform and converts
   its output to TAXSIM format.
5. [`../common/compare.py`](../common/compare.py) compares the two
   outputs, writes the differences to the `work/differences/` folder,
   and prints a summary of them.

Steps 3-5 are shared with the [`pe_taxsim`](../pe_taxsim/README.md)
workflow and are described in detail in its README; here each is run
with `--workflow tbly_ts`, which makes it use this folder, the
`ts_output/` folder, and the `ts_emulation.json` reform.
`validate.py` in this folder runs them (see
[Running all the steps](#running-all-the-steps)).

The samples and TS outputs are committed, so steps 3-5 can be rerun
using only the `taxcalc-dev` conda environment: neither
tax-simulator-gpu nor its environment is needed.  Generated working
files are written to the git-ignored `work/` folder.

Other files in this folder:

- [`VARIABLES.md`](VARIABLES.md) documents how each TAXSIM input
  variable is translated into tax-simulator-gpu inputs and how
  tax-simulator-gpu outputs are converted into TAXSIM output variables
  (the Tax-Calculator translations are those in
  [`../pe_taxsim/VARIABLES.md`](../pe_taxsim/VARIABLES.md)).
- [`ts_pin.json`](ts_pin.json) pins the tax-simulator-gpu commit;
  `update_ts_pin.py` updates the pin (see
  [Updating the TS pin](#updating-the-ts-pin)).
- [`ts_emulation.json`](ts_emulation.json) is the Tax-Calculator
  reform that adopts tax-simulator-gpu's modeling conventions (full
  EITC and ACTC take-up and no Schedule R credit).
- [`SUMMARY.md`](SUMMARY.md) explains the differences.

Rerunning the comparison
------------------------

From the top-level repository folder, in the `taxcalc-dev` conda
environment, run:

```
python taxcalc/validation/tbly_ts/validate.py
```

This runs steps 3-5 for all nine samples (letters `a`, `b`, `c`
times years 2023-2025) in about thirty seconds and prints a summary
of the differences for each sample.  The `test.sh` script (run by
`make valtest` after the `pe_taxsim` test) runs `validate.py` and
checks that its output is the same as the committed
`test_results.expect` file.  A difference means that a Tax-Calculator
change altered at least one compared result: examine the
`work/differences/LYY-taxdiffs.csv` file for each sample whose
summary changed and decide whether the change fixes a bug (then
regenerate `test_results.expect` and update [`SUMMARY.md`](SUMMARY.md))
or whether the Tax-Calculator change introduces a bug.

Results summary
---------------

Output generated by `validate.py` includes the pinned
tax-simulator-gpu version and results for 10,000 random filing units
in each sample.  The three sample ASSUMPTION SETS generate
increasingly complex tax units:

- `a`: wages, ages of head and spouse, and up to three dependents;
- `b` ADDS TO `a`: pensions, Social Security benefits, dividends, interest,
  capital gains and losses, unemployment compensation, rental income,
  and self-employment, business, and S-corporation income (each of
  the last three nonzero in only 25% of units);
- `c` ADDS TO `b`: property taxes, mortgage interest, other itemized
  deductions, and child care expenses (for tax units with at least one
  dependent under age 13).

The same twenty-three TAXSIM output variables are compared as in the
`pe_taxsim` workflow (see [`VARIABLES.md`](VARIABLES.md)).  All of
them agree to within $1 except for those summarized in the
`test_results.expect` file.  tax-simulator-gpu is run with its own
default tax law, unchanged, so every difference between its tax law
parameter values and the IRS and SSA published values that
Tax-Calculator uses shows up as a difference between the models.
[`SUMMARY.md`](SUMMARY.md) explains every difference: the 0.7 factor
tax-simulator-gpu applies to net investment income when computing the
net investment income tax (a deliberate calibration), its 2024-2025
OASDI maximum taxable earnings, its married filing separately 20%
capital gains bracket, and its smoothed child tax credit and child
care credit phase-outs.

Validation of a new tax year
----------------------------

To add a year, change the `tbly_ts` `last_year` in
`../common/workflows.py` and `LAST_YEAR` in `run_ts.py`, check that
the pinned tax-simulator-gpu law covers the new year, check that
Tax-Calculator's `policy_current_law.json` contains the IRS and SSA
published values for the new year, check the year-specific logic in
`../common/run_tc.py`, `run_ts.py`, and [`VARIABLES.md`](VARIABLES.md)
for the new year's law changes, generate the samples and TS outputs
for the new year (steps 1 and 2), and examine every difference the
way the existing ones were examined before regenerating
`test_results.expect`.

Environment setup
-----------------

Steps 1, 3, 4, and 5 run in the `taxcalc-dev` conda environment from
the top-level repository folder, so the working-tree Tax-Calculator
code is the code being validated.

Step 2 runs tax-simulator-gpu in its own Python environment, which
needs Python 3.12 and a pinned version of JAX, so nothing is ever
installed in `taxcalc-dev`.  `run_ts.py` itself runs in `taxcalc-dev`
and uses [uv](https://docs.astral.sh/uv/) to make that environment
(`uv sync --locked --no-dev` in the clone, which installs exactly the
package versions in the clone's `uv.lock` file and, if needed,
downloads Python 3.12) and to run `ts_batch.py` in it.  `run_ts.py`
finds `uv` on the `PATH` (or uses the `--uv` option or the
`TBLY_TS_UV` environment variable).  `ts_batch.py` imports nothing from
Tax-Calculator: it runs tax-simulator-gpu's `taxmodel.run.batch`
command, which computes income and payroll taxes for a file of tax
units under one year's law, and leaves out the estate tax.

tax-simulator-gpu is used from a clone of its repository at the commit
pinned in `ts_pin.json`, kept outside this repository, by default in
`~/.cache/tbly_ts/tax-simulator-gpu-<sha>` (or the folder given by the
`--tsdir` option or the `TBLY_TS_DIR` environment variable).
`run_ts.py` makes a shallow clone of the pinned commit if the folder
does not exist and refuses to run if the clone is at another commit or
has modified or untracked files (the git-ignored `.venv` folder that
uv makes is allowed).  tax-simulator-gpu's own data inputs, which are
not public, are not needed.

`python run_ts.py L YYYY` runs step 2 for one sample.  It refuses to
overwrite an existing TS output unless `--force` is given, and it
checks that the output has the expected columns and the same
`taxsimid` and `year` values as the input sample, and that the batch
command used the default law of the sample year, all-zero random draws,
and every tax unit column supplied to it.  A 10,000-unit run takes
about five seconds.  `python run_ts.py --all` runs all nine samples,
using three concurrent processes unless `--jobs N` specifies a
different number.  The TS outputs are byte-reproducible.

Tax law
-------

tax-simulator-gpu builds its 2023-2025 baseline tax law from the YAML
files in its `config/scenarios/tax_law/default/` folder, indexing some
parameters with price and wage indexes.  `ts_batch.py` runs the batch
command with the `--bundled-macro` option, which makes it read those
indexes from the copy of the pinned Macro-Projections publication in
the tax-simulator-gpu repository (`resources/macro_projections/`), so
they are pinned along with the tax-simulator-gpu commit.  The law is
never changed: any tax-simulator-gpu parameter value that differs
from the IRS or SSA published value, whether because of indexation or
because of a YAML file value, shows up as a difference between the
models, which [`SUMMARY.md`](SUMMARY.md) explains and which can be
reported to the Budget Lab.

Updating the TS pin
-------------------

tax-simulator-gpu is under active development, so change the pin only
deliberately.  `python update_ts_pin.py` finds the newest commit on
tax-simulator-gpu's default branch using the GitHub API, checks that it
contains the tax-simulator-gpu files `run_ts.py` and `ts_batch.py`
use, and reports each `ts_pin.json` entry that would change, the
number of commits between the pinned and the new commit, and which of
the files that can affect the TS outputs (`pyproject.toml`, `uv.lock`,
`src/taxmodel/` except its calibration and reporting code, the default
tax law and economy configurations, and
`resources/macro_projections/`) those commits changed.  GitHub lists at
most 300 changed files, so when there are more the script says so, and
the changed files must be listed with `git diff --stat OLD NEW` in a
tax-simulator-gpu clone that has both commits.  It is a dry run unless
`--write` is given, which updates `tax_simulator_sha`,
`tax_simulator_sha_date`, and `pinned_on`.  Use `--sha SHA` to pin a
specific tax-simulator-gpu commit instead of the newest one.  The
Python package versions are pinned by the `uv.lock` file of the pinned
commit, so they need no separate pin.  After writing a new pin,
regenerate all nine TS outputs with `python run_ts.py --all --force`,
recheck the statements about tax-simulator-gpu in
[`VARIABLES.md`](VARIABLES.md) (in particular, `ts_batch.py` fails if
the batch command reads a tax unit column that `run_ts.py` does not
supply, and `run_ts.py` fails if it supplies a column that the batch
command does not read), re-examine every difference, update
[`SUMMARY.md`](SUMMARY.md), and regenerate `test_results.expect`.

Regenerating everything
-----------------------

This command sequence regenerates all nine samples and TS outputs,
regenerates all the Tax-Calculator outputs, and compares the results
with the committed `test_results.expect`.  Run these from
`taxcalc/validation/tbly_ts`, in the `taxcalc-dev` conda environment,
with `uv` installed:

```
cd taxcalc/validation/tbly_ts

# 1. regenerate all 9 samples into samples/
python ../common/generate_sample.py --all --workflow tbly_ts

# 2. regenerate all 9 TS outputs into ts_output/ (--force allows overwriting)
python run_ts.py --all --force

# 3+4+5. regenerate the TC outputs in work/ and run the comparisons
python validate.py > test_results.actual

# see what changed relative to the committed results
diff test_results.actual test_results.expect
```

The "3+4+5" command is equivalent to the `tbly_ts` part of
"make valtest" in the top-level folder of the repository.

Running all the steps
---------------------

`python validate.py` runs steps 3-5 for every letter and year using
the committed samples and TS outputs and prints each comparison; its
exit code is 0 only when every step runs without error.
Use `--letters` (e.g., `ab`) and `--years` (e.g., `2023,2025`) to
run a subset, and `--tolerance` to change the tolerance (default $1).

With `--regen`, `validate.py` first runs steps 1 and 2
(`../common/generate_sample.py` and `run_ts.py --force`), which
**overwrites** the samples and TS outputs.  Do that in the committed
folders only deliberately.  `--datadir DIR` makes `validate.py` use
the `samples`, `ts_output`, and `work` folders in `DIR` instead of
those in this folder, so a quick trial run with a small sample leaves
the committed files alone:

```
python validate.py --letters a --years 2023 --regen --size 100 \
    --datadir /some/scratch/folder
```
